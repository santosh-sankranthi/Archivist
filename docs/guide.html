Ask your repository anything — on the web, GitHub, or Slack. It remembers.

Archivist turns a codebase and its history into a living FalkorDB graph, then answers multi-hop engineering questions with traceable reasoning: every claim cites code, commits, or documents — and every answer is stored in the same graph, so the next session, on any surface, can recall it.

What is Archivist?

Archivist is an engineering-intelligence agent. Point it at a repository and it ingests the code, the git history, and the project documentation into one FalkorDB graph. A tool-calling agent then answers questions about that repository by querying the graph — call chains, churn, ownership, archaeology, docs — and posts the answer wherever you work: a web console, a GitHub issue, a Slack thread.

Grounded answers, never guessesEvery answer cites files, symbols, line numbers, commits, and doc sections. When evidence is weak or missing, it says so.
Cross-session memoryAnswers become graph nodes. Reference an earlier issue or discussion on any surface — it recalls it, with the original link.
Three surfaces, one brainConsole, GitHub issues, and Slack mention/DMs run the same agent, the same tools, the same graph, the same memory.
Graph-nativeImpact analysis, dependency walks, shortest call paths, ownership, time-machine history — real Cypher, shown with every answer.
Bring your own modelAny OpenAI-compatible endpoint (OpenAI, OpenRouter, vLLM, OpenCode Zen…). Keys can stay in your browser; the server never logs them.
Auditable by designRead-only queries only, idempotent writes, guesses flagged — and the full trace (tools + Cypher) for everything it claims.

The demo graph is the falkordb-py Python client — a real repository with real history. Archivist ships as a general pipeline (scripts/ingest.py accepts any checkout).

Try it in 3 minutes

Pick any of the three doors. They all talk to the same brain, and everything you do is remembered in the same graph.

1 · Web console
  1. Open the live console.
  2. Ask: “How do I create a vector index?” — watch the live step feed, then the answer with citations.
  3. Click any session in the left rail to re-open it read-only from memory.
2 · GitHub issues
  1. Open the demo fork → Issues → New issue.
  2. Ask a real question about the repo (e.g. “Where is the query timeout enforced?”).
  3. Within ~1–2 minutes the agent replies on your thread — with file/symbol citations, and labels if it's a bug report.
3 · Slack
  1. Join the workspace.
  2. In a channel, run /invite @archivist — then @archivist how do I create a vector index? (DMs work too).
  3. The answer lands in-thread in ~1–2 minutes — and it's stored in the shared memory.
The party trick: once something has been asked anywhere — a GitHub issue, a Slack thread, a console session — ask any other surface about it by topic or issue number (“what's the status of issue 3?”). It answers from memory and links the original thread.

Core concepts · One graph per repo

Everything Archivist knows lives as nodes and edges in FalkorDB. The same graph holds three kinds of knowledge — and every answer is a read-only Cypher query over it (GRAPH.RO_QUERY is enforced by the database, not by convention).

KnowledgeNodesAnswers questions like…
Code & history Repo · Commit · Author · File · Symbol · Module
edges: DEFINES, CALLS, IMPORTS, MODIFIED, AUTHORED, PARENT, HEAD		 Who calls this? What breaks if it changes? Who should review it? When did it last change, and why?
Documentation DocPage (1,541 ingested sections for the demo graph) What do the docs say about vector indexes, configuration, clients…?
Memory Episode · Fact
edges: PRODUCED, ABOUT, SUPERSEDES, HANDOFF		 What did we discuss before? What was concluded about this file? What's the status of issue 3?

Design rules: every write is an idempotent MERGE (re-ingest converges, never duplicates) · best-effort CALLS edges are flagged weak and excluded by default with the filtered count reported · memory is append-only — a contradicted fact closes its validity window and links its replacement, it is never deleted.

Core concepts · The agent loop

The agent is deliberately thin: the model chooses tools, the tools run as read-only Cypher, and compact result envelopes go back to the model until it answers. The full trace — every tool call, every query, every timing — is kept on the answer, and the console replays it on the graph canvas as an induced subgraph.

Honesty contract: answers must be built from tool results only. Weak (guessed) call edges are off by default and counted when filtered; unresolved anchors and caps are reported in the result envelopes; if the graph can't answer, the agent says what's missing instead of improvising.

Core concepts · Memory across sessions

This is the part that makes Archivist more than a chatbot: every session on every surface is recorded into the graph, and later sessions can recall it.

  • Episodes — one node per session: the question and the stored answer, tagged by surface (agent-session from the console, github-answer from issues — carrying the issue's URL — slack-answer from Slack, plus ingest runs and crew phases).
  • Facts — durable findings the agent chose to keep, with bi-temporal windows: “true now”, full history, or “what was true at time T”.
  • Recall matches your question by keyword tokens and by issue/PR numbers (“issue 3”, “#3”, “pull request 7” — typo-tolerant), resolving numbers against the original session's URL. Results are ranked by match strength and carry the source link.
Recipe — watch the USP in action: ask something on the GitHub fork (or use an existing thread like issue 3, “Feature request: list indexes from the Python client”). Then ask the console or Slack: “what's the status of issue 3?” — the answer cites the original GitHub thread by URL, plus what the code says today. That's the same graph reading, not a cached chat.

The console's Memory view is the ledger: every episode from every surface, facts with their validity windows, and proposed actions — all browsable.

GitHub guide

The demo repository is a fork (santosh-sankranthi/falkordb-py) with the Archivist GitHub App installed. Open an issue there with any real question about the repo:

  • Question → a grounded answer comment on the thread (file/symbol/doc citations).
  • Bug report → triage labels + a missing-information checklist where relevant.
  • First-time author → a short welcome, recorded as a gh-first-seen episode (so later sessions know the person is new).

Two more paths into the repository:

  • From the console: press “File as GitHub issue” on any answer — the question lands on the fork as a real issue, and the agent replies on the thread. The web surface acting on the repository.
  • Existing threads: issues #1–#6 are previous live runs — read them to see the answer style, then ask your own.
Timing: webhook → answer comment typically within 1–2 minutes. The answer is also stored as a github-answer episode with the issue URL — which is what makes issue-number recall work elsewhere.

Slack guide

  3. Mention it: @archivist how do I create a vector index, and when should I use one? — or simply DM the app.

API guide

The console is a client of a small HTTP API served by the same box. Everything the UI does, you can do with curl.

# ask the agent (JSON: answer + full trace)
curl -s -X POST https://figure-them-trucks-concentrate.trycloudflare.com/api/ask \
  -H 'Content-Type: application/json' \
  -d '{"question": "Who calls Graph.query?"}' | head -c 800

# stream it (Server-Sent Events: step_start / step_result / answer_delta / done)
curl -N -X POST https://figure-them-trucks-concentrate.trycloudflare.com/api/ask/stream \
  -H 'Content-Type: application/json' \
  -d '{"question": "What breaks if QueryResult._parse_records changes?"}'

Bring your own LLM key

Override the server's model per request with headers — the server never stores or logs them:

curl -s -X POST .../api/ask \
  -H 'Content-Type: application/json' \
  -H 'X-Archivist-LLM-Base: https://openrouter.ai/api/v1' \
  -H 'X-Archivist-LLM-Model: your-model' \
  -H 'X-Archivist-LLM-Key: sk-...' \
  -d '{"question": "..."}'
Demo-key asks are capped per client per hour (429 past the cap, with a hint to bring a key). Responses are bounded and the server limits concurrent work, so a burst of stalled connections can't take the box down.

Testing guide for judges

Everything below is testable live, in order. Times assume the free demo model; the console's step feed shows progress while you wait. Total: ~10 minutes for the full pass, ~3 for the essentials (steps 1, 4, 6).

1 · Console — ask, watch, verify (~2 min)

  1. Open /console/ and ask: “How do I create a vector index, and when should I use one?”
  2. Expect: live step cards (tool name, args, rows, ms) → a streaming answer with inline citations → a trace ribbon of the Cypher that ran.
  3. Click a session in the left rail → a read-only peek opens with the stored answer (including sessions from GitHub/Slack — the badges tell you which surface).

2 · Explorer — the graph under the answers (~1 min)

  1. Search list_indices → open the symbol in Explorer.
  2. Expect: callers/callees with counts, weak guesses excluded (and reported); run the path finder between two symbols.

3 · Memory — the ledger (~1 min)

  1. Open Memory. Expect: your console ask from step 1 listed as an agent-session; earlier github-answer and slack-answer sessions too.
  2. Look at Actions: proposed next steps from past runs, with done/superseded controls (bi-temporal — closing is never deleting).

4 · GitHub — real issues, real answers (~2 min)

  1. On the demo fork, open a new issue asking a real question (or read issues #1–#6 for prior live runs).
  2. Expect: an answer comment within ~1–2 min — cited to files/symbols/docs; bug reports get triage labels.

5 · Slack — the same brain in a thread (~2 min)

  1. Join via the invite, /invite @archivist in a channel, then mention it with a question.
  2. Expect: threaded answer in ~1–2 min, footer confirming shared memory.

6 · Cross-session memory — the USP (~1 min, no waiting)

  1. Ask the console (or Slack, or the API): “what's the status of issue 3?”
  2. Expect: an answer citing the original GitHub thread URL (…/issues/3) — recalled from the graph by issue number, not appended by hand.
  3. Optional: ask something new in Slack, then find that session in the console's left rail — every surface writes to the same memory.

7 · API — verify the machine (~1 min)

curl -N -X POST https://figure-them-trucks-concentrate.trycloudflare.com/api/ask/stream \

Troubleshooting / FAQ

The Ask room says asking is disabled / HTTP 503

The box runs without a server-side model key in that case — the explorer stays fully live. Open Settings in the console and bring your own OpenAI-compatible key (it's kept in your browser and sent per request only).

HTTP 429 when asking

You hit the per-client demo-key quota. Either wait for the hourly window or bring your own key in Settings — unlimited and private.

The Slack bot didn't answer

  • In channels it only reacts to an explicit @archivist mention — plain messages are ignored by design.
  • The app must be in the channel: run /invite @archivist.
  • DMs work with any message (no mention needed). Give it up to ~2 minutes.

The GitHub comment didn't appear

Make sure the issue is on the fork (santosh-sankranthi/falkordb-py) — that's where the app is installed. Give it ~2 minutes; the webhook is verified and signature-checked (deliveries show 202).

An answer says “cannot determine” / “unknown”

That's the honesty policy, not a failure: weak call edges are excluded (the filtered count is reported), unresolved anchors are surfaced, and the agent is instructed to state what's missing instead of guessing. It's part of why the answers you do get are trustworthy.

Answers take 30–90 seconds

Real multi-step tool calling over a live graph on a free demo model — the console streams every step so you can watch it work. On your own key/model it's as fast as your model.

Where is the memory stored? Can I inspect it?

In the same FalkorDB graph as the code. GET /api/graph/memory returns the full timeline; the console's Memory view renders it; POST /api/cypher lets you query it read-only yourself.

Can I run Archivist on my own repository?

Yes — see the README: Docker Compose (FalkorDB + console), scripts/ingest.py accepts any checkout, and the GitHub/Slack adapters are environment-configured.

Under the hood

repo + docs + history→ ingest (idempotent)→ FalkorDB graph→ agent loop (read-only tools)→ console · GitHub · Slack · API
  • Ingest (src/archivist/ingest.py) walks the git history and source tree, resolves call edges by name with layered confidence (rings), ingests documentation pages, and ensures lookup indexes. Re-runs converge.
  • The agent (src/archivist/agent.py) is a thin, auditable loop: model → tool calls → compact envelopes → final answer, with the full trace preserved. Memory tools (recall/remember/act) share the same graph.
  • Surfaces all run the same runner: the stdlib webapp serves the console + API + webhooks; the Slack and GitHub adapters hand questions to the same core and post answers back. One brain, three doors.
  • Crew mode (planner → investigator → verifier) enforces tool scopes per role and records phase handoffs as graph edges — the coordination history is queryable like everything else.
  • Deploys run through a self-hosted CI on the same box: pytest + console tests gate the deploy, the console is rebuilt when it changes, the service restarts, and a smoke test must pass before the deploy is reported.
Known limits, stated plainly: the demo runs a free model (answer quality varies; retries on empty finalizations) · resolver-heavy anchors can plan as scans on FalkorDB today (index-shape tuning is logged work) · the console's demo key is quota-limited by design. The full honest ledger lives in the README and docs/graph-model.md.
